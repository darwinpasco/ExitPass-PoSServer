# ExitPass POS Server DB Validation / Rebuild Workflow Plan

## 1. Purpose

This document defines the planned future workflow for POS Server database clean rebuild, validation, and drift-check evidence. It prepares for later scripts but does not create scripts.

## 2. Workflow Principles

- Repository state is the source of truth.
- Rebuild uses a disposable clean database.
- Validation reports facts; it does not rewrite SQL artifacts.
- Drift is reported and never auto-promoted.
- Accepted drift must become reviewed repository changes.
- Authority-boundary validation is required for every DB artifact PR.

## 3. Clean Database Creation

Future scripts should create or connect to a disposable PostgreSQL database. The database must be local or CI-scoped and must not be a live production or shared authority database.

The future workflow should record:

- database host/connection alias, without secrets;
- PostgreSQL version;
- database name;
- whether the database was created, reused, or reset;
- timestamp of rebuild start and finish.

## 4. SQL Application Order

Future application order for the current first-slice scope:

1. `db/state/schemas/pos.sql`
2. `db/state/tables/pos.controlled_code_sets.sql`
3. `db/state/tables/pos.controlled_codes.sql`
4. `db/state/tables/pos.site_pos_servers.sql`
5. `db/state/tables/pos.fiscal_identities.sql`
6. `db/state/tables/pos.site_pos_server_fiscal_identity_history.sql`
7. `db/state/tables/pos.channel_terminals.sql`
8. `db/state/tables/pos.channel_terminal_capabilities.sql`
9. `db/state/tables/pos.channel_terminal_status_history.sql`

This order applies schema first, controlled-code foundation second, identity/boundary objects third, channel registry fourth, and dependent capability/status-history objects last.

## 5. Optional SQL Smoke Check

Future smoke checks should use `psql` or an approved PostgreSQL client against a disposable database. The smoke check should apply the files in order and fail on any syntax/application error.

If no local PostgreSQL client is available, the future process should report the smoke check as skipped and rely on static validation until CI support exists.

## 6. Schema Inventory

Future schema inventory should capture at minimum:

- schema name;
- schema owner if available;
- schema comment;
- unauthorized schemas under POS Server artifact scope.

Expected current schema: `pos`.

## 7. Object Inventory

Future object inventory should capture:

- tables by schema;
- object type;
- file source if available;
- unexpected objects;
- missing approved objects.

Expected current first-slice tables:

- `pos.controlled_code_sets`
- `pos.controlled_codes`
- `pos.site_pos_servers`
- `pos.fiscal_identities`
- `pos.site_pos_server_fiscal_identity_history`
- `pos.channel_terminals`
- `pos.channel_terminal_capabilities`
- `pos.channel_terminal_status_history`

## 8. Constraint and Index Inventory

Future validation should capture:

- primary key constraints;
- foreign key constraints and referenced tables;
- unique constraints;
- check constraints;
- indexes generated by constraints;
- standalone indexes, if later approved;
- identifier lengths greater than PostgreSQL limits.

The current first slice does not create standalone indexes.

## 9. Naming Validation

Future naming validation should check:

- `pos` schema use;
- lowercase `snake_case` identifiers;
- no quoted identifiers;
- internal IDs end in `_id`;
- external references end in `_ref` or use approved source prefix;
- Central PMS references use `central_pms_*_ref` where applicable;
- no identifier exceeds PostgreSQL's 63-byte identifier limit.

## 10. Authority-Boundary Validation

Future checks must fail if object, column, constraint, or comment text implies POS Server ownership of:

- payment finality;
- PaymentAttempt lifecycle;
- PaymentConfirmation lifecycle;
- ExitAuthorization;
- gate execution authority;
- independent terminal fiscal authority;
- offline fiscal issuance approval.

Reference-only Central PMS names remain allowed when explicitly named as references.

## 11. Prohibited Object Validation

Future validation must confirm absence of prohibited object families unless a later approved task adds them:

- fiscal document and Sales Invoice objects;
- fiscal line/tender/tax/discount/total objects;
- numbering/counter/GTA objects;
- idempotency objects;
- Digital SI URL/token/access objects;
- reprint and adjustment objects;
- report/export/EJ/POSLog objects;
- audit objects;
- recovery/anchoring objects;
- outbox/event objects.

## 12. Drift Report

Future drift-check workflow should compare repository state to a rebuilt or live test database and classify:

- missing expected objects;
- unexpected objects;
- changed definitions;
- constraint/index drift;
- comments/documentation drift where tooling supports it;
- controlled-code/reference-data drift once those artifacts exist.

The report must not modify SQL files or promote live state.

## 13. PR Evidence Capture

A future DB artifact PR should include:

- SQL file inventory;
- clean rebuild result;
- smoke-check result or explicit skip reason;
- schema/object inventory;
- constraint/index inventory;
- naming validation result;
- authority-boundary validation result;
- prohibited-object validation result;
- drift-check result;
- no local drift promotion confirmation.
